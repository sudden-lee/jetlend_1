# Заказы с промокодами

Django-проект для тестового задания: `POST /api/orders/` создаёт заказ и применяет
процентную скидку к подходящим товарам. Python 3.10+, Django 5.2 LTS,
PostgreSQL 16.
HTTP API реализован на Django REST Framework: `APIView`, отдельные входные и
выходные serializers, session authentication и CSRF.

## Правила применения промокода

| Правило | Где проверяется |
| --- | --- |
| Промокод должен существовать | `_lock_promo`, код ошибки `promo_not_found` |
| Не должен быть просрочен (`expires_at`) | `_lock_promo`, `promo_expired` |
| Ограничение на максимум использований (`max_uses`/`uses_count`) | `_lock_promo`, `promo_limit_reached`; инвариант `uses_count <= max_uses` защищён и в БД |
| Один пользователь не может использовать код повторно | `_lock_promo`, `promo_already_used`; `UNIQUE(user, promo_code)` на `PromoCodeRedemption` |
| Может быть ограничен категорией товаров | `PromoCode.category` (nullable FK), проверка в `_build_lines` |
| Товары с исключением из акций (`excluded_from_promotions`) | проверка в `_build_lines`; если ни одна строка не подошла — `promo_not_applicable`, лимит не расходуется |

Реализация — `orders/services.py`.

## Локальный запуск

Перейдите в `task1` и выполните в PowerShell:

```powershell
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements-dev.txt
docker compose up -d --wait
.venv/Scripts/python.exe manage.py migrate
.venv/Scripts/python.exe manage.py createsuperuser
.venv/Scripts/python.exe manage.py seed_demo
.venv/Scripts/python.exe manage.py runserver
```

`compose.yaml` запускает PostgreSQL 16 на `127.0.0.1:55432`; локальные значения
по умолчанию: БД `task1`, пользователь `task1`, пароль `task1-local`. Их можно
переопределить переменными `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`,
`POSTGRES_HOST` и `POSTGRES_PORT`. При `DJANGO_DEBUG=0` пароль обязателен и
локальное значение по умолчанию не используется.

`migrate` создаёт схему PostgreSQL. Команда `seed_demo` создаёт товар
по цене 100 и промокод `SUMMER2025`: скидка 10%, срок действия 30 дней, лимит
100 использований. Она печатает ID товара и безопасно повторяется, если данные
совместимы. Существующие объекты команда не изменяет: товар с тем же именем, но
другими свойствами не используется, а занятый несовместимым или просроченным
`SUMMER2025` приводит к понятной `CommandError` без частичных изменений.
На Linux/macOS используйте `.venv/bin/python` вместо `.venv/Scripts/python.exe`.

`createsuperuser` создаёт администратора только для управления данными. Откройте
[админку](http://127.0.0.1:8000/admin/): категории, товары и промокоды можно
создавать и изменять, а заказы, их строки и журнал погашений доступны только для
просмотра, чтобы история покупок не исправлялась вручную. Списки используют
русские названия, поиск, фильтры и загрузку связанных объектов без N+1. Создайте
отдельного активного пользователя без прав staff и используйте его как покупателя. Затем откройте
[вход](http://127.0.0.1:8000/accounts/login/): после входа страница показывает
`user_id`. Заказы в админке доступны только для просмотра.

## Контракт API

`POST /api/orders/`, `Content-Type: application/json`. Требуются активная
сессия пользователя, CSRF-токен и заголовок `Idempotency-Key`. Ключ содержит
1–128 ASCII-символов из `A-Z`, `a-z`, `0-9`, `.`, `_`, `:`, `-` и уникален в
пределах пользователя. `user_id` должен совпадать с ID вошедшего пользователя:
создание заказа от чужого имени запрещено.

```json
{
  "user_id": 1,
  "goods": [{"good_id": 1, "quantity": 2}],
  "promo_code": "SUMMER2025"
}
```

Успешный ответ — HTTP 201 с заголовком `Idempotency-Replayed: false`:

```json
{
  "user_id": 1,
  "order_id": 1,
  "goods": [
    {"good_id": 1, "quantity": 2, "price": 100, "discount": "0.1", "total": 180}
  ],
  "price": 200,
  "discount": "0.1",
  "total": 180
}
```

`price` в строке — цена одной единицы товара на момент заказа; `total` — итог
строки с учётом количества и скидки. В заказе `price` — сумма `price × quantity`,
а `total` — сумма итогов строк.
`price` и `total` в JSON — числа. Ставка скидки — десятичная строка
(`"0.1"` означает 10%): это сохраняет точность доли при передаче между
системами. Без промокода скидка равна `"0"`.

Повтор того же валидированного запроса с тем же ключом возвращает тот же заказ,
HTTP 201 и `Idempotency-Replayed: true`. Ключ с другим `user_id`, составом
корзины, количеством или промокодом считается другим запросом и получает 409.
Срок хранения ключа — не менее 24 часов: истёкшие записи удаляет команда
`python manage.py purge_idempotency_keys`, которую в размещении следует запускать
по расписанию. Пока запись не удалена, повтор остаётся безопасным.

Допускаются 1–100 строк, положительные целочисленные ID и количество 1–10000.
Повторяющиеся `good_id` отклоняются: количество нужно объединить в одну строку.
Дробные числа и `bool` вместо ID/количества отклоняются.
Размер тела ограничен 64 KiB. Необязательное `promo_code` можно опустить;
передавать `null` или пустую строку нельзя. Код чувствителен к регистру,
содержит 1–64 символа ASCII: латинские буквы, цифры, `_`, `-`.

Ошибки бизнес-правил возвращаются в формате:

```json
{"error": {"code": "promo_expired", "message": "Promo code has expired."}}
```

| HTTP | Причина / `error.code` |
| --- | --- |
| 400 | Невалидный JSON/поля (`invalid_request`) или отсутствующий/невалидный ключ (`invalid_idempotency_key`) |
| 403 | Нет активной сессии, неверный CSRF или чужой `user_id` (`forbidden`) |
| 404 | Один или несколько товаров отсутствуют (`goods_not_found`) |
| 405 | Метод, отличный от POST (`Allow: POST, OPTIONS`) |
| 409 | Промокод уже использован (`promo_already_used`), исчерпан (`promo_limit_reached`) или ключ повторён с другим запросом (`idempotency_conflict`) |
| 413 | Слишком большое тело (`request_too_large`) |
| 415 | Тип тела, отличный от JSON |
| 422 | Промокод отсутствует (`promo_not_found`), просрочен (`promo_expired`) или не подходит ни одному товару (`promo_not_applicable`) |

DRF выполняет аутентификацию, CSRF, разбор JSON и проверку метода до вызова
бизнес-сервиса. Ошибки serializer возвращают `invalid_request` и объект
`details` с ошибками конкретных полей. Ошибки протокола DRF возвращает в своём
стандартном JSON-формате `detail`.

Бизнес-ошибки (`OrderError`) форматирует общий
`REST_FRAMEWORK["EXCEPTION_HANDLER"]` (`orders.exceptions.api_exception_handler`):
код и HTTP-статус каждой ошибки заданы там же, где она поднимается.

## Расчёт и сохранение

Промокод действует, пока `expires_at > timezone.now()`. Он может ограничиваться
одной категорией; товары с `excluded_from_promotions=True` всегда исключены.
В смешанной корзине скидка применяется только к подходящим строкам. Если таких
строк нет, заказ отклоняется без расходования лимита. Если строки есть,
использование учитывается даже при округлении денежной скидки до нуля.

Цены и итоги хранятся в PostgreSQL `numeric` через Django `DecimalField`;
вычисления от чтения цены до записи результата используют только `Decimal`.
Цена единицы ограничена диапазоном 0,01–10 000 000,00. Вместе с ограничениями корзины
это исключает переполнение БД.
Для строки сначала умножается цена на количество, затем применяется скидка
и итог округляется до сотых по `ROUND_HALF_UP`. Ставка строки — номинальная
ставка промокода; ставка заказа — фактическая `(price - total) / price`,
округлённая до четырёх знаков по `ROUND_HALF_UP`. Поэтому ставка заказа может
отличаться от ставки промокода при исключениях и округлении.

`Category`, `Good`, `PromoCode`, `Order`, `OrderItem`, `PromoCodeRedemption` и
`OrderIdempotencyKey` — модели приложения `orders`. Заказ сохраняет снимки цен,
скидок и итогов: изменение
каталога не меняет существующие заказы. Отдельная запись погашения сохраняет
факт использования промокода даже после удаления заказа. Ограничение
`UNIQUE(user, promo_code)` на этой таблице обеспечивает буквальное правило
«один пользователь — одно применение». `PromoCode.uses_count` позволяет проверять
общий лимит за O(1), а ограничение `uses_count <= max_uses` защищает инвариант в БД.
Журнал погашений остаётся источником аудита.
Текущая схема нового проекта собрана в одной миграции `0001_initial`.

Проверка правил, заказ, погашение и строки записываются в одной транзакции.
PostgreSQL блокирует выбранный `PromoCode` через `select_for_update`, поэтому
проверка и увеличение общего лимита для одного кода выполняются последовательно.
Разные промокоды не блокируют друг друга. Ключ идемпотентности, заказ, строки,
погашение и счётчик записываются одной транзакцией; при любой ошибке откатываются
вместе. Товары загружаются одной выборкой, строки создаются через `bulk_create`.

Сервис повторяет всю транзакцию не более трёх раз только для PostgreSQL SQLSTATE
`40001` (serialization failure) и `40P01` (deadlock), с короткой экспоненциальной
задержкой. Ошибки валидации, бизнес-правил, ограничения БД и потеря соединения не
повторяются вслепую. Сам HTTP-клиент может безопасно повторить запрос с тем же
ключом. Endpoint ограничен DRF throttling до 120 запросов в минуту на пользователя.

## Границы решения

Поддерживается только PostgreSQL. Тесты используют отдельную PostgreSQL test DB;
пользователю БД нужны права на её создание. `CONN_MAX_AGE` по умолчанию равен
нулю для предсказуемого локального запуска и настраивается одноимённой
переменной окружения после измерения нагрузки.

Остатки, оплата, налоги и внешняя очередь не моделируются: в задании нет их
контрактов. Если endpoint запускается несколькими процессами или экземплярами,
для точного общего throttling нужно настроить общий Django cache (например Redis);
локальный `LocMemCache` ограничивает каждый процесс отдельно. Идемпотентность и
лимит промокода от cache не зависят и обеспечиваются PostgreSQL.

Настройки по умолчанию предназначены для локальной разработки. Для размещения
задайте `DJANGO_DEBUG=0`, собственный `DJANGO_SECRET_KEY`,
`DJANGO_ALLOWED_HOSTS` и настройте HTTPS, безопасные cookies и веб-сервер.
`check --deploy` в этом режиме оставляет два предупреждения о HSTS для
поддоменов и preload; эти параметры нужно выбирать для конкретного домена.
